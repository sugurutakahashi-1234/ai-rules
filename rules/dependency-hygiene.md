# 依存の扱い

依存管理は 4 つの別の仕事に分かれる。ひとくくりに「更新ツール」を入れると、1 つ塞いだつもりで他が空く。

| 仕事 | 防ぐ事故 |
|---|---|
| 待つ | 公開直後の汚染パッケージを踏む |
| 固める | 同じものが入らない / タグをすり替えられる |
| 上げる | 固めたまま古びる |
| 気づく | 脆弱性・滞留・仕組みの停止に気づけない |

## 待つ（cooldown）

乗っ取られた npm パッケージは、公開から数時間〜数日でレジストリから消される。待つだけで大半を避けられる。

- `bunfig.toml` に `[install] minimumReleaseAge = 259200`（3 日、単位は秒）。pnpm は同名の設定、Dependabot は 2026-07 から既定で 3 日待つ
- **「最新に上げたのに最新にならない」のは、この設定が効いている正常な動作。** 上がらないからと外さない
- lockfile に既にあるバージョンには効かない（bun#30525）。これは「これから新しく解決されるもの」への防御であって、今入っているものの安全を保証しない
- プロジェクト直下に置く。`~/.bunfig.toml` は無視される（bun#30750）
- 待てない依存が出たら `minimumReleaseAgeExcludes` に個別に足す。増やすほど穴になるので最小限に

依存の更新を AI エージェントに任せる運用では、人の「なんだか新しすぎる」という勘が挟まらないぶん、この待ち時間の価値が高い。

## 上げる

更新 bot（Renovate / Dependabot version updates）を入れるかは、**その PR をレビューする人がいるか**で決める。

- レビュアーが実質 1 人なら、bot の PR は「誰も開かない通知」になる。自動マージを止めた時点で bot の主価値（放置しても上がる）は失われている
- 入れないと決めたら、**上げる係を明示的に置く**。SHA ピンも lockfile も「壊れないが古びる」ので、担当を決めないと誰も上げなくなる
- bot が PR を作らない期間が続いたとき、それが「更新が無い」のか「設定で構造的に作られない」のかを確かめる。`rangeStrategy` とレンジ表記と lockfile 設定の組み合わせで、仕様上 PR が一切作られない状態になりうる

## 気づく

- 脆弱性アラート（Dependabot alerts 等）は有効にする。**PR を作る機能（security updates / version updates）とは別物**で、独立して on/off できる。アラートだけ受け取って PR は作らせない選択ができる
- 言語横断で見る。`bun audit` は lockfile を読むので、同じリポジトリの Python / Actions / Terraform の依存は一切見えない。「緑＝安全」と誤読しない
- **直せない advisory の扱いを先に決める。** 修正版が公開されていない脆弱性を放置すると検査が毎回赤くなり、「赤いのが常態」になって本物の検出まで見落とす。理由と**再評価期限**を書いて緑に戻し、期限を過ぎたら自動で赤へ戻す形にする。期限の無い除外はいずれ忘れられる
