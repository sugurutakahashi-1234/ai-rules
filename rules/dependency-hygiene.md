# 依存の扱い

依存管理は 4 つの別の仕事に分かれる。ひとくくりに「更新ツール」を入れると、1 つ塞いだつもりで他が空く。

| 仕事 | 防ぐ事故 |
|---|---|
| 待つ | 公開直後の汚染パッケージを踏む |
| 固める | 同じものが入らない / タグをすり替えられる |
| 上げる | 固めたまま古びる |
| 気づく | 脆弱性・滞留・仕組みの停止に気づけない |

## 待つ（cooldown）

乗っ取られた npm パッケージは、公開から数時間〜数日でレジストリから消される。待つだけで大半を避けられる。

- `bunfig.toml` に `[install] minimumReleaseAge = 259200`（3 日、単位は秒）。pnpm は同名の設定、Dependabot は 2026-07 から既定で 3 日待つ
- **「最新に上げたのに最新にならない」のは、この設定が効いている正常な動作。** 上がらないからと外さない
- lockfile に既にあるバージョンには効かない（bun#30525）。これは「これから新しく解決されるもの」への防御であって、今入っているものの安全を保証しない
- プロジェクト直下に置く。`~/.bunfig.toml` は無視される（bun#30750）
- 防いでいるのは「乗っ取り版が検知・削除されるまでの数時間に当たること」。乗っ取り型はスキャナ（Socket / Aikido 等）が公開直後に見つけて数時間で消えるのが通例だが、install した側の被害は削除では戻らない。潜伏型（event-stream / xz）には効かない

依存の更新を AI エージェントに任せる運用では、人の「なんだか新しすぎる」という勘が挟まらないぶん、この待ち時間の価値が高い。

**待機は既定であって絶対ではない。貫通するかは人が決める。** AI エージェントは、待機で最新が入らないとき黙って古い版に倒さず、次の 4 点を添えて「最新に上げるか」を聞く:

1. 公開からの経過時間
2. provenance（ビルド元の証明）が付いているか。盗んだトークンからの公開には付かないことが多い
3. install script や新しい依存が増えていないか（乗っ取り版の典型パターン）
4. 開発ツール（実行範囲が手元と CI）か、バンドルされて利用者へ届くものか

貫通すると決まったら、リポジトリの `minimumReleaseAgeExcludes` は増やさない（恒久の穴になる）。設定ファイルを一時ファイルにコピーして除外を足し、`--config=` で 1 回だけ使う。**コミット本文に「待機を人の承認で迂回: <pkg>@<ver>（公開 N 時間後）」と 1 行残す**。リポジトリの設定に痕跡が残らないので、理由は git に残す。

lockfile に公開直後の版が入っていないかの監査は、止めるゲートにせず気づくための定期レポートに置く。人が承認して入れた版を CI で赤にしても意味がない。

## 固める

lockfile と `package.json` は固めている場面が違う。

- **lockfile が固めるのは install。** コミットして CI で `--frozen-lockfile` を使っていれば、`package.json` の範囲（`^` / `~`）があっても無くても入る版は同じ
- **`package.json` の範囲が効くのは `bun update` を打った瞬間だけ。** `^` のままだと範囲内の全パッケージが黙って動き、差分は lockfile にしか出ない（lockfile の diff は人も AI も読み飛ばす）

AI エージェントが依存を更新する運用では、**アプリケーションのリポジトリは範囲をやめて完全固定にする**（bun は `bunfig.toml` の `[install] exact = true`）。更新が「人が読むファイルへの明示的な編集」になり、`bun update` では何も動かなくなる。`~` は安全にも見えるようにもならないので選ばない。

- 「固定すると競合して入らない」はほぼ起きない。通常の依存は版が食い違っても入れ子で両方入るだけで、失敗するのは `peerDependencies` の不一致だけ（それは `^` でも防げない）。直接依存を固定しても間接依存は各パッケージ自身の範囲で解決される
- 固定が本当に困るのは **npm に公開するライブラリ**（利用側に重複を強いる）。アプリなら気にしなくてよい
- **monorepo では `catalog` とセットにする。** ルートの `package.json`（bun は `workspaces.catalog`）に版を 1 回だけ書き、各 workspace は `"pkg": "catalog:"` で参照する。固定だけだと workspace ごとに別の固定値を書いてズレていく（react や zod が 2 重にバンドルされる）。catalog なら版を書く場所がパッケージあたり 1 箇所になり、AI の更新は「catalog の 1 行を書き換えて `bun install`」で済む
- 移行は lockfile の解決済みの版をそのまま書き写す。入るものは 1 つも変わらないので低リスク。移行後は `bun update` を使わない（固定値を再解決しに行くだけで、待機中の版があるとエラーで止まる）。更新は catalog / `package.json` を編集して `bun install`
- 意図的な据え置き（互換性待ちの pin）は版だけでは見分けられなくなる。理由と再開条件を Issue に残す

## 道具の置き場（mise か package.json か）

開発ツールを mise（`latest`）に置くか `package.json`（固定）に置くかは、**「CI がその道具を動かすか」**で決める。「開発環境 = latest / アプリの SDK = 固定」という区分は、「人が使う = latest / 機械が使う = 固定」と言い換えるとぶれない。

- **CI が動かす道具 → `package.json` に固定。** CI は `setup-bun` + `bun install --frozen-lockfile` で動く。deploy パイプラインの道具が `latest` だと、誰も push していないのに道具の更新でデプロイが落ちる。lint / 型検査 / 生成物の drift 検知に使うもの（typescript / oxlint / oxfmt / knip / syncpack / commitlint / rulesync / dotenvx / clasp 等）はここ。版が変わると検査結果や生成物が変わるものは、名前が「道具」でも SDK として扱う
- **人（と git hook）だけが使う道具 → mise で `latest`。** 壊れても手元で気づけるし、最新の恩恵をすぐ受けられる。terraform / gcloud / gh / aws-cli 等
- **CI が mise-action 経由で動かす検査ツール（gitleaks / pinact / actionlint / shellcheck）は mise `latest` でよい。** 成果物に影響せず、落ちたら「新しい検知が増えた」で、それは知りたい情報
- **同じ道具を両方に置くのは、人が素のコマンドで叩く実需があるときだけ。** 例: `dotenvx run -f .env.cli -- bun …` を人が打つリポでは mise にも置く。実需が無い重複は package.json 側に一本化する（`prepare: lefthook install` は `bun install` が `node_modules/.bin` を PATH に通すので npm 版で足りる）
- **ランタイム（node 等）はメジャーだけ人が決めて固定し、マイナーは `latest`**（`node = "26"`）。`latest` にすると奇数の非 LTS メジャーへ勝手に飛び、CI の `setup-node` とズレる。メジャーを上げるときは全リポ一斉に変える
- mise の `latest` は各マシンが `mise install` した時点で止まる（`mise.lock` が無ければ）。「latest のつもり」を保つには `mise up` を回す係が要る。これも「上げる係を置く」の一部

## 上げる

AI エージェントが上げる時代の原則:

- **頻繁に、小さく上げる。ただし公開直後は入れない。** 頻度と鮮度は別物で、頻度は高いほど 1 回の差分が小さく壊れても原因を絞れる。鮮度は「待つ」で下げる。数か月放置してからメジャーをまたぐのが一番危ない
- **人は「何を」を決め、AI は「どう」を実行する。** 「最新にして」を丸投げしない。release notes は人（か対話している親エージェント）が読み、対象と版を決めて合意してから AI に実行と検証をさせる。人が見るべき箇所を更新の後（PR レビュー）から前（対象の決定）へ移す
- **AI が止まって人に返す線**: 待機の例外への追加、メジャーバージョンをまたぐ更新、意図的な pin の解除、lockfile で推移依存のメジャーが動いたとき
- **検証の無いリポジトリでは AI に上げさせない。** AI 更新の安全性はそのリポジトリのテストと型検査の質で決まる。無ければ先に足すか、手動更新のままにする
- ガードレールは指示文ではなくハーネス（設定ファイル・pre-commit・CI の `needs`）に置く。AI が「やらない」ではなく「できない」状態にする。ただし `--config=` のように迂回できるものは残るので、迂回を禁じるより「迂回は人が決め、痕跡を残す」を規約にする

更新 bot（Renovate / Dependabot version updates）を入れるかは、**その PR をレビューする人がいるか**で決める。

- レビュアーが実質 1 人なら、bot の PR は「誰も開かない通知」になる。自動マージを止めた時点で bot の主価値（放置しても上がる）は失われている
- 入れないと決めたら、**上げる係を明示的に置く**。SHA ピンも lockfile も「壊れないが古びる」ので、担当を決めないと誰も上げなくなる
- bot が PR を作らない期間が続いたとき、それが「更新が無い」のか「設定で構造的に作られない」のかを確かめる。`rangeStrategy` とレンジ表記と lockfile 設定の組み合わせで、仕様上 PR が一切作られない状態になりうる

## 気づく

- 脆弱性アラート（Dependabot alerts 等）は有効にする。**PR を作る機能（security updates / version updates）とは別物**で、独立して on/off できる。アラートだけ受け取って PR は作らせない選択ができる
- 言語横断で見る。`bun audit` は lockfile を読むので、同じリポジトリの Python / Actions / Terraform の依存は一切見えない。「緑＝安全」と誤読しない
- **直せない advisory の扱いを先に決める。** 修正版が公開されていない脆弱性を放置すると検査が毎回赤くなり、「赤いのが常態」になって本物の検出まで見落とす。理由と**再評価期限**を書いて緑に戻し、期限を過ぎたら自動で赤へ戻す形にする。期限の無い除外はいずれ忘れられる
