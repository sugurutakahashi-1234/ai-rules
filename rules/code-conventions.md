# コーディング規約

## 変更の範囲

依頼された範囲が成果物で、それを黙って広げない・狭めない。今のモデルは周辺のコードまで直したり、頼まれていないテストや抽象化を足したりしやすいので、線を明示しておく。

- 作業中に見つけた既存のバグ・性能の懸念・依頼に無い挙動は、依頼の動作がそれ無しでは成立しない場合を除いて、この変更では直さない。最後の報告に「別件」として書く
- 依頼が曖昧なら、文面と周辺コードが最も素直に支持する読みで実装し、その前提を報告に書く。他の読み方のぶんまで作らない
- テストは依頼がある箇所か、そのリポジトリが同種の変更にテストを持っている箇所にだけ足す。粒度は隣のテストファイルに合わせる。動作確認に使った使い捨てスクリプトを永続的なテストに昇格させない
- 検証の量は変更のリスクに比例させる。1 行の修正に全スイートは要らないし、共有モジュールの変更なら影響先まで回す
- 起こりえない状況の防御コード・一度しか使わない処理のヘルパー・将来の要件を見越した設定項目は足さない。境界（ユーザー入力・外部 API）でだけ検証する

## 変更の作法

- 恒久的なファイルは既存ファイルの編集を優先し、新設は構造上の必要があるときだけにする。検証用の使い捨てスクリプトは作ってよいが、作業ディレクトリではなく scratchpad に置き、終わったら消す
- 「意図的な重複」をコメントの言い訳で残さない。同じ実装が 2 箇所に要るなら共有の置き場へ昇格させる
- 小さな変更でファイル全体を書き直さない。差分が小さいほどレビューも巻き戻しも楽になる

## コメント

WHY だけを残す。以下は書かない。

- WHAT（コードを読めば分かること）
- 日付・履歴・変更差分
- TODO の進捗
- `// =====` のような区切り線

## TypeScript

- `strict` を有効にする
- `null` は意味のある不在にのみ使う。ありえないケースや degenerate なケースは `""` や自然な既定値に倒し、無意味な null 分岐や第三の状態を作らない

## 時刻

内部は UTC、表示は JST。DB / API は UTC の ISO 8601 で持ち、UI 表示のタイミングで JST に変換する。
