# 環境変数と秘密の置き場所

秘密は「ファイルに書く」のではなく「保管庫に置いて、ファイルには参照を書く」。PC が壊れても鍵が残り、人に渡すときは保管庫の権限単位で済むようにするため。

## .env の扱い

- `.env` は dotenvx で暗号化してコミットする。平文の `.env` を `.gitignore` で隠す運用にしない（値がリポジトリの外に散り、複数人・複数マシンで同期する手段が無くなる）
- `.env.keys` と `DOTENV_PRIVATE_KEY` の実値はコミットしない。鍵の正本はパスワード保管庫（1Password・Bitwarden など）に置く
- `.env` に秘密を書くときは値ではなく保管庫参照を書き、dotenvx に解決させる（`op://<vault>/<item>/<field>`・`bw://<item>/<field>`）。どの保管庫を使うかはマシン側の指示に従い、このルールでは決めない
- CI には `DOTENV_PRIVATE_KEY` だけを secrets で渡す。個別の値を CI の secrets に増やすと、ローカルと CI で正本が 2 つになる

## 落とし穴

- 参照の解決に失敗する（保管庫が未解錠・CLI 未インストール・アイテム名の変更）と、dotenvx は参照文字列をそのまま環境変数に入れて続行する（dotenvx/dotenvx#950）。「接続できない」ではなく「値がおかしい」として現れるので、まず保管庫の解錠状態を疑う
- 公開前提の識別子（リソース ID・ブラウザに配信されるキー）は秘密ではないので暗号化も参照化も要らない。秘密かどうかの判断基準は `secret-safety` と同じ
