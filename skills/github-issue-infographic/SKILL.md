# github-issue-infographic（GitHub issue にインフォグラフィックを差し込む）

issue の Markdown 本文（文章・表・コードブロック）は変えず、各章の見出し直後に「読む前の地図」となる 1 枚絵を差し込む。GitHub の issue 本文は HTML をサニタイズして `<style>`・class・インライン CSS を落とすので、CSS で組んだ図解は表示されない。表示できるのは画像・Mermaid・テーブル・`> [!NOTE]` アラート程度で、リッチな図解は画像化して issue に添付するのが唯一確実な経路。

呼び出し規約（Codex 経由・課金回避・`< /dev/null`・並列一括生成・生成後の確認）は image-gen が正本で、ここには issue 版固有のことだけを書く。食い違ったら image-gen を優先する。

## 進め方

GitHub の読み書きは `gh` CLI（ローカル認証済み）だけで行う。GitHub MCP コネクタはプライベートリポジトリで 404 を返して読めないことがあるので、失敗してからフォールバックするのではなく最初から `gh` を使う。

1. `gh issue view <N> --repo <owner>/<repo> --json number,title,body` で本文を取る。`##` 見出しを章とみなし、既定では各章に 1 枚。冒頭の注記だけの章は外してよい
2. 代表的な 1 枚（フロー章か表章）を試作してトーン・密度・タイトル感を合わせ、残りを並列で一括生成する。確定した画像は作業用ディレクトリ（`.tmp/issue-<N>/<NN>-<slug>.png` 等、コミットしない場所）に集める
3. 各章見出しの直後に `![<alt>](./<NN>-<slug>.png)` を 1 行入れる。alt は内容の要約。相対パスは `--attach` が添付先の URL へ書き換える
4. `gh issue edit <N> --body-file <tmp> --attach '<path>#<alt>'`（画像ごとに `--attach` を繰り返す。1 コマンド 50 件まで、gh 2.100.0 以降）で本文と添付を一度に更新する。本文の相対参照は添付先へ書き換えられ、リポジトリに画像を置かないので commit / push は要らない

## 画像の置き場所と参照

- ファイル名: `<章番号 2 桁>-<英語 slug>.png`（例 `03-project-lifecycle.png`）。添付後は GitHub 側の asset URL に置き換わるので、作り直すときはもう一度 `--attach` する
- 画像をリポジトリに残したい事情があるとき（資料と一緒に版管理したい等）だけ、`docs/assets/issue-<N>/` に置いて commit / push し、`https://github.com/<owner>/<repo>/raw/main/...` で参照する。この場合は画像を push してから本文を更新する（逆順だと一瞬リンク切れになる）。GitHub は画像を camo proxy でキャッシュするので、差し替えはファイル名を変える

## スタイル定型（プロンプト冒頭に貼る）

実運用の社内マニュアル issue で磨き込んだ「親しみやすいが可愛すぎない・情報多め・フロー明快」トーン。プロンプト冒頭に以下を貼る:

```
組み込みの image_gen ツールを直接使って画像を1枚だけ生成してください。APIキーやスクリプト作成は不要です。OpenAI Images APIを直接叩かないでください。

【スタイル】手書き風のやさしいフラットイラスト。少しデフォルメした親しみやすいキャラ（にっこり笑顔）。可愛くしすぎず、画面をごちゃごちゃさせない。キャラ・小物は小さめに添えて文字情報を主役にする。落ち着いた配色で「情報が整理されて見やすい」ことを最優先。ロボットBotは丸くフレンドリーに。背景はベージュの紙(#f7f2e7)。お金・書類・スマホなどの小物もシンプルにデフォルメ。

【タイトル見出し】上部にしっかりした「見出し」を置く：左に小さな丸い色アイコン＋セクション番号バッジ（例：01）、その右に大きな太字タイトル、タイトル文字の下にマーカーで引いたような太い色帯（ハイライト）を敷く。本文よりはっきり大きく、ひと目でタイトルと分かるデザインにする。
【フロー】手順・流れは大きな番号＋矢印で順番が一目で追えるレイアウトにする。担当が分かれる場合は色で区別（スタッフ=青／管理者=オレンジ／自動・Bot=緑 など）し、担当ラベルを添える。

【情報量】ギチギチに多めにする。角丸の情報カードの中に「太字の見出し＋箇条書き 2〜3 行」を文字で入れ、本文の見出し・補足・表・担当ラベルを逐語でしっかり文字で描く。カード・ブロックは点線や矢印でつないで視線の流れを作る。文字だけでも内容が伝わる密度にし、余白を広く取りすぎない。文字は太めで読みやすく、誤字なく正確に整理して配置する。

【禁止】星・鉛筆・絵筆・水彩の飛び散り、本文に関係ない動物などのにぎやかし装飾は描かない。リアルすぎる人物や固い事務的な雰囲気は避ける。
【サイズ】横1536 x 縦1024。
日本語は誤字なく正確に描いてください。
```

そのうえで `【描く内容：<章タイトル>】` として、その章の**正確なテキスト**（タイトル・本文の要点・表の各セル・リストの各項目・担当）を箇条書きで渡す。表は「A｜B｜C」の区切りで列を明示すると崩れにくい。

### スタイルのキモ

- タイトルには見出し化の指定（アイコン＋番号バッジ＋マーカー下線）を入れる。指定しないと本文と同じ太字になり締まらない
- 可愛さは中庸。「絵本風・ちびキャラ全開」にすると情報が減って軽くなる
- 装飾の禁止を明示する。指定しないと星・鉛筆・水彩・無関係な動物が散る
- 文字は間引かない。本文の箇条書き・表・補足を逐語でカード内に詰め込む（逐語で渡せば高密度でも崩れない）。キャラが大きく余白が広い「かわいいポスター」はトーン違い。文字だけでも内容が伝わる密度が好まれる
- 人物キャラ（スタッフ・管理者・担当者などデフォルメしたにっこり人物）も入れる。Bot・システムだけだと AI 感が強まる。過去に合意済みの実例 PNG があればその密度に合わせる

### 合格基準

成果物は「読みやすい図表」ではなく、手書き風イラスト入りインフォグラフィック。文字精度を理由に HTML/CSS/Playwright/SVG で図表画像を組む方向には逃げず、画像内テキストを短く正確な語句に絞って描かせる。各画像には、人物、Bot、スマホ・通知画面、書類・契約書・請求書、スプレッドシート・台帳、お金、フォーム・チェックリストのうち 3 種類以上を目に見えるイラストとして入れる。

文字が正確でも不合格になるもの: 角丸カードと矢印だけの業務フロー図、HTML/CSS で整えた説明スライド風の画像、小物がほぼない図表、マスコット 1 体＋ラベル数個だけのスカスカなポスター。試作の 1 枚で「小物が十分か」「図表だけになっていないか」「文字だけでも章の内容が伝わる密度か」を見て、満たさなければ残りを生成せずその 1 枚を作り直す。最終確認では全画像をまとめて（サムネイル一覧で）「社内マニュアル向けの手書き風イラスト群」に見えるか確認し、図表・カード UI に見えるものは差し替える。

## 差し込み例

```markdown
## 全体の流れ（案件 1 件のライフサイクル）

![全体の流れ：①案件決定→②管理者確認→③契約台帳反映→…→⑦消込。担当はスタッフ/管理者/自動で色分け](./03-project-lifecycle.png)

① 案件が決まる …（既存本文はそのまま）
```

## やらないこと

- 本文の文章・表・コードブロック・リンクを書き換えない（差し込むのは画像行だけ）
- HTML/CSS で図を組んで issue に貼らない（レンダリングされない）
- イラストのみで文字を入れない作り方をしない（読めない絵になり、全差し替えになった失敗がある）
- raw URL 方式を選んだときは、画像を push する前に issue 本文を更新しない（リンク切れになる）
- 大量の章を確認なしに一括生成しない。1 枚合意してからバッチ
