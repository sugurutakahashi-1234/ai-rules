# github-issue-infographic Skill（GitHub issue にインフォグラフィックを差し込む）

> **Core Principle**: issue の Markdown 本文（文章・表・コードブロック）は内容を変えない。各章の見出し直後に「読む前の地図」となる1枚絵を差し込むだけ。図解は **Codex 経由の image_gen（gpt-image-2）で生成した「手書き風イラスト＋正確な日本語テキスト」画像**。GitHub の issue Markdown は `<style>`/CSS が無効なので、HTML/CSS で図を組んでもレンダリングされない → 必ず画像化して raw URL で参照する。

## なぜ画像生成ルートなのか（HTML/CSS ではない理由）

- GitHub issue 本文は HTML をサニタイズし `<style>`・class・インライン CSS のほとんどを落とす。md-to-visual-html のような CSS 図解はそのままでは表示できない。
- 表示できるのは「画像（`![]()`）・Mermaid・テーブル・`> [!NOTE]` アラート」程度。リッチな図解は **画像にするのが唯一確実**。
- gpt-image-2 は **プロンプトに正確な日本語文字列を渡せば、その文字をほぼ正しく描く**。「文字を入れない（イラストのみ）」プロンプトにすると読めない絵になるので、**必ず本文テキストを文字として描かせる**。

> **共通エンジン / 姉妹スキル**: gpt-image-2 の呼び出し作法（Codex経由・API課金回避・生成後レビュー・1枚試作→合意→一括）と「画像内に文字を入れるなら逐語の正確な文字列を渡して文字化けを防ぐ」原則は、姉妹スキル `md-to-visual-html` と共通。
>

> **md-to-visual-html との関係（スタイルは基本同じ方針）**: 図解スタイル（**文字多め**のイラスト＋正確な文字・タイトル見出し化・番号＋矢印のフロー）は姉妹スキル md-to-visual-html と共通でよい。**どちらも文字はギチギチに多めでよい**（gpt-image に逐語の正確な文字列を渡せば高密度でも崩れない。「文字は少なめに」は誤り）。違いは媒体由来の機構だけ：md-to-visual-html は出力が HTML なので画像を相対パスで参照でき、必要なら CSS 図解・表も併用できる。本スキルは issue が CSS 無効なので全部画像化し、commit→raw URL で参照、装飾（星・鉛筆・水彩）は入れない。

## 全体ワークフロー

> **GitHub アクセスは `gh` CLI のみ**: issue の取得・更新はすべて `gh`（ローカル認証済み）で行う。**GitHub MCP コネクタは使わない** — プライベートリポジトリでは MCP が 404 を返して読めないことがある。MCP で取りに行って失敗→フォールバック、ではなく最初から `gh` を使う。

1. **対象 issue の特定**: `gh issue view <N> --repo <owner>/<repo> --json number,title,body` で本文を取得。リポジトリは URL から判定する。
2. **最新化**: プロジェクト方針に従い、作業前に `git pull --ff-only`。`main` で作業。
3. **章構成の把握**: 本文の `##` 見出しを章とみなす。**default は各章に1枚**（md-to-visual-html の章扉と同じ思想）。冒頭の注記ブロックだけの章はスキップ可。
4. **章ごとにプロンプトを起こす**: 後述の【スタイル定型】＋【その章の正確なテキスト】。表・リスト・担当ラベルは**本文から逐語コピーして文字列で渡す**（gpt-image の創作・誤字を防ぐ）。
5. **Q&A で1枚試作 → 合意 → 一括生成**: いきなり全章作らない。まず代表的な1枚（フロー章 or 表章）を生成して見せ、トーン・密度・タイトル感を合わせてから残りを生成する。

6. **画像生成（Codex 経由・サブスクルート）**: 下記「画像生成」の通り。生成物は `~/.codex/generated_images/<id>/*.png` に出る。試作の1枚は最新ファイル（`ls -t ~/.codex/generated_images/*/*.png | head -1`）を拾えばよいが、**合意後の残りは並列で一括生成する**（下記「複数枚の並列一括生成」）。確定した画像を `docs/assets/issue-<N>/<NN>-<slug>.png` へコピーしてマッピングする。

7. **レビュー（必須）**: 生成画像を1枚ずつ `Read` で開き、**文字化け・誤字・内容違い**がないか確認。崩れていたらその章だけ再生成。台帳名・区分など意味が変わる誤字は特に厳しく見る。
8. **本文へ差し込み**: 各章見出しの直後に `![<alt>](<raw URL>)` を1行入れる。**本文の文章・表・コードは触らない**。alt は内容の要約（スクリーンリーダ・検索用）。
9. **コミット → プッシュ → issue 更新（順序厳守）**: raw URL は `main` 上の画像を指すので、**画像を先に commit/push**してから `gh issue edit <N> --body-file <tmp>` で本文を更新する。逆順だと一瞬リンク切れになる。

## 画像の置き場所と参照

- 置き場所: 対象リポジトリの資産規約に従った `docs/assets/issue-<N>/` 相当のディレクトリ。
- ファイル名: `<章番号2桁>-<英語slug>.png`（例 `03-project-lifecycle-illustrated.png`）。時系列・対応が追える命名にする。
- 参照 URL（raw）:
  `https://github.com/<owner>/<repo>/raw/main/<path>/docs/assets/issue-<N>/<NN>-<slug>.png`
- **キャッシュ注意**: GitHub は画像を camo proxy でキャッシュする。同名で中身だけ差し替えると反映が遅い／古い絵が出ることがある。作り直すときは**ファイル名（or 拡張子）を変えて URL を変える**とキャッシュを確実に外せる。

## スタイル定型（gpt-image-2 プロンプトに必ず入れる）

実運用の社内マニュアル issue で磨き込んだ「親しみやすいが可愛すぎない・情報多め・フロー明快」トーン。プロンプト冒頭に以下を貼る:

```
組み込みの image_gen ツールを直接使って画像を1枚だけ生成してください。APIキーやスクリプト作成は不要です。OpenAI Images APIを直接叩かないでください。

【スタイル】手書き風のやさしいフラットイラスト。少しデフォルメした親しみやすいキャラ（にっこり笑顔）。可愛くしすぎず、画面をごちゃごちゃさせない。キャラ・小物は小さめに添えて文字情報を主役にする。落ち着いた配色で「情報が整理されて見やすい」ことを最優先。ロボットBotは丸くフレンドリーに。背景はベージュの紙(#f7f2e7)。お金・書類・スマホなどの小物もシンプルにデフォルメ。

【タイトル見出し】上部にしっかりした「見出し」を置く：左に小さな丸い色アイコン＋セクション番号バッジ（例：01）、その右に大きな太字タイトル、タイトル文字の下にマーカーで引いたような太い色帯（ハイライト）を敷く。本文よりはっきり大きく、ひと目でタイトルと分かるデザインにする。
【フロー】手順・流れは大きな番号＋矢印で順番が一目で追えるレイアウトにする。担当が分かれる場合は色で区別（スタッフ=青／管理者=オレンジ／自動・Bot=緑 など）し、担当ラベルを添える。

【情報量】ギチギチに多めにする。角丸の情報カードの中に「太字の見出し＋箇条書き 2〜3 行」を文字で入れ、本文の見出し・補足・表・担当ラベルを逐語でしっかり文字で描く。カード・ブロックは点線や矢印でつないで視線の流れを作る。文字だけでも内容が伝わる密度にし、余白を広く取りすぎない。文字は太めで読みやすく、誤字なく正確に整理して配置する。

【禁止】星・鉛筆・絵筆・水彩の飛び散り、本文に関係ない動物などのにぎやかし装飾は描かない。リアルすぎる人物や固い事務的な雰囲気は避ける。
【サイズ】横1536 x 縦1024。
日本語は誤字なく正確に描いてください。
```

そのうえで `【描く内容：<章タイトル>】` として、その章の**正確なテキスト**（タイトル・本文の要点・表の各セル・リストの各項目・担当）を箇条書きで渡す。表は「A｜B｜C」の区切りで列を明示すると崩れにくい。

### スタイルのキモ（ハマりどころ）

媒体によらない共通の作法（**逐語で文字を渡す・カタカナ長音＋「一」の崩れ・生成後レビュー**）は共有スキル `image-gen` の「プロンプト共通の作法とハマりどころ」に従う。ここには issue 版固有のキモだけを挙げる:

- **タイトルは必ず「見出し化」の指定を入れる**（アイコン＋番号バッジ＋マーカー下線）。指定しないと本文と同じ太字になり締まらない。
- **可愛さは中庸**。「絵本風・ちびキャラ全開」にすると情報が減って軽くなる。「親しみやすいが整理されている」を狙う。
- **装飾の禁止を明示**。指定しないと星・鉛筆・水彩・無関係な動物が散る。

- **文字は間引かない**。「画像だから文字は少なめに」を理由に語数を絞らない。本文の箇条書き・表・補足を**逐語で**カード内に詰め込む（逐語で渡せば高密度でも崩れない）。キャラが大きく余白が広い「かわいいポスター」はトーン違い（2026-07 のユーザーフィードバック: 文字ギチギチ・文字だけでも内容が伝わる密度が好まれる）。
- **章が長い場合も情報は削らない**。見出し・固有名詞・数字は逐語のまま落とさず、その章だけで完結させる。表もそのまま描かせてよい。
- **人物キャラ（スタッフ・管理者・担当者などデフォルメしたにっこり人物）も入れる**。Bot・システムだけだと AI 感が強まる。トーンの基準は過去に合意済みの実例 PNG（あれば）——「人物＋情報カード＋点線＋手描きの線」の密度に合わせる。

### イラスト品質の合格基準（必須）

このスキルの成果物は「読みやすい図表」ではなく、**手書き風イラスト入りインフォグラフィック**。文字精度を理由に HTML/CSS/Playwright/SVG で図表画像を組むのは禁止。文字化けが不安な場合は、HTML図表へ逃げず、画像内テキストを短く・正確な語句に絞って gpt-image-2 に描かせる。

各インフォグラフィックには、少なくとも次のうち **3種類以上** を目に見えるイラストとして入れる:

- 人物（スタッフ / 管理者 / 担当者など）
- フレンドリーな Bot
- LINE のスマホ画面・通知画面
- 書類・契約書・請求書・勤務表
- スプレッドシート / 台帳
- お金・入金・支払を示す小物
- フォーム・メール・チェックリストなど、その章固有の道具

次のような成果物は、たとえ文字が正確でも不合格:

- 角丸カードと矢印だけの業務フロー図
- HTML/CSS で整えた説明スライド風の画像
- 人物・Bot・LINE・書類・お金などの小物がほぼない図表
- 「読みやすいが、手書き風イラスト入りではない」画像
- スキルのスタイル定型にある小物・キャラ指定が反映されていない画像
- マスコット1体＋ラベル数個だけのスカスカなポスター（キャラが大きく余白が広く、文字情報が薄い画像）

1枚試作の確認では、文字の正確さだけでなく、**人物 / Bot / LINE / 書類 / お金などが十分に入っているか**、**図表だけになっていないか**、**情報量がギチギチか（文字だけでも章の内容が伝わる密度か）**を確認する。満たさない場合は残りを生成せず、その1枚を作り直す。

最終レビューでは、全画像のサムネイル一覧（コンタクトシート）を作り、9枚なら9枚まとめて「社内マニュアル向けの手書き風イラスト群」に見えるか確認する。一覧で図表・カードUIに見えるものは差し替える。

## 画像生成（Codex 経由・API 課金を発生させない）

Codex の組み込み `image_gen`（gpt-image-2）を使う（Claude Code 自身は画像生成できないため Codex CLI 経由で呼ぶ）。**ChatGPT サブスク内で完結させ、API 従量課金ルートに入らないこと**（プロジェクトのエージェント指示と同方針）。呼び出し規約の**正本は共有スキル `image-gen`**（同じ共有層から配布。前提としてこのスキルと併せて導入する）。本節はその要約で、食い違う場合は image-gen を優先する。

**手順・注意（前提確認・呼び出し方・ハング打ち切り基準・保存の注意・`parallel-imggen.sh` による複数枚の並列一括生成）は、共有スキル `image-gen` の「画像生成」「複数枚の並列一括生成」にそのまま従う**（エンジンの手順・数値をここに複製しない）。本スキル向けの読み替えは次だけ:

- スクリプトの場所: image-gen スキルの `scripts/parallel-imggen.sh`
- ジョブルートの例: `/tmp/imggen-issue-<N>/`
- 確定した画像のコピー先: `images/` ではなく `docs/assets/issue-<N>/<NN>-<slug>.png`
- issue 用サイズは横 1536 × 縦 1024 が扱いやすい（ベージュ背景前提なので透過は不要。生成はほぼ余白なしに収まるため後段クロップも不要）
- image-gen 側の「置き場所」はリポジトリ規約に委ねられているが、本スキルでは「画像を先に commit / push → issue 更新」の順序が正

並列化しても「1枚試作 → 合意 → 残りを一括」の順序と、生成後のレビュー（1枚ずつ開いて誤字確認。Claude Code の場合は `Read` ツールで開く）は省略しない。

## issue 本文への差し込み例

章見出しの直後に画像1行を足すだけ（本文はそのまま）:

```markdown
## 全体の流れ（案件1件のライフサイクル）

![全体の流れ：①案件決定→②管理者確認→③契約台帳反映→…→⑦消込。担当はスタッフ/管理者/自動で色分け](https://github.com/<owner>/<repo>/raw/main/docs/assets/issue-4/03-project-lifecycle-illustrated.png)

① 案件が決まる …（既存本文はそのまま）
```

## やらないこと / 注意

- 本文の文章・表・コードブロック・リンクを書き換えない（差し込むのは画像行だけ）。
- HTML/CSS で図を組んで issue に貼らない（レンダリングされない）。図解は必ず画像化。
- HTML/CSS/Playwright/SVG で「画像化した図表」を作って代替しない。最終成果物は、ユーザーが明示しない限り gpt-image-2 で生成した手書き風イラスト入り画像にする。
- イラストのみで文字を入れない作り方をしない（読めない絵になる。過去にこの失敗をして全差し替えになった）。
- 画像を push する前に issue 本文を更新しない（リンク切れになる）。
- 大量の章を**確認なしに一括生成しない**。1枚合意してからバッチ。
- 確定した内容（金額・台帳名・区分）が画像で誤字になっていないか必ず目視。意味が変わる誤字は再生成。
```
