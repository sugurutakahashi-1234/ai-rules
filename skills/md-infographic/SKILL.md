# md-infographic Skill（ローカル Markdown にインフォグラフィックを差し込む）

> **Core Principle**: Markdown 本文（文章・表・コードブロック）は内容を変えない。各章の見出し直後に「読む前の地図」となる1枚絵を差し込むだけ。図解は **Codex 経由の image_gen（gpt-image-2）で生成した「手書き風イラスト＋正確な日本語テキスト」画像**。出力は Markdown のまま（HTML 化しない）なので、GitHub 上のレンダリング・エディタのプレビュー・共有ページのいずれでもそのまま見られる。

## 姉妹スキルとの使い分け

| スキル | 媒体 | 出力 | 画像参照 |
|---|---|---|---|
| md-to-visual-html | ブラウザ向けページ | 単一 HTML（再設計あり） | 相対パス |
| github-issue-infographic | GitHub issue | issue 本文更新 | commit 済み画像の raw URL |

| slide-infographic 等の媒体スキル（ある場合） | Marp スライド | スライドへの画像記法追記 + 画像配置 | 相対パス |

| **md-infographic（本スキル）** | リポジトリ内 Markdown | **同じ md ファイルへの画像行追記のみ** | **相対パス** |

> **共通エンジン**: gpt-image-2 の呼び出し作法（Codex経由・API課金回避・生成後レビュー・1枚試作→合意→一括）と「画像内に文字を入れるなら逐語の正確な文字列を渡して文字化けを防ぐ」原則は、姉妹スキルと共通。本スキルではさらに、Markdown の各章を**中心メッセージ＋大きな視覚メタファー＋高密度な周辺情報**で見せる章扉向けのスタイル定型を使う。**文字は多めでよい**（gpt-image に逐語の正確な文字列を渡せば高密度でも崩れにくい。「文字は少なめに」は誤り）。

## 全体ワークフロー

1. **対象 Markdown の特定**: ファイルパスをユーザーから受け取る（IDE で開いているファイル・直前に作った資料が文脈で明らかならそれ）。作業前にプロジェクト方針に従い `main` で最新化（資料作成直後の続き作業なら pull 不要）。
2. **章構成の把握**: 本文の `##` 見出しを章とみなす。**default は各章に1枚**だが、章数が多い資料（10章超）では「読者の理解を助ける章」に絞る提案をしてユーザーと合意する。スキップ候補: 注記だけの章、出典一覧、メタ情報、他章の繰り返しになる章。
3. **章のビジュアル設計**: 各章について「中心メッセージ（読後に1つだけ残したいこと）」「大きな視覚メタファー」「紙面の主役」「周辺に置く比較・注意・結論」を先に決める。本文をカードへ分解するだけでは、手書き風でも説明スライドにしかならない。章の意味を、階段・合流する道路・橋・天秤・建物・循環・分かれ道などの**一目で関係性が伝わる大きな絵**へ翻訳する。
4. **画像プランの提示**: 「章｜中心メッセージ｜視覚メタファー｜周辺情報」の一覧を短く出して合意を取る。同じ構図を全章へ機械的に使い回さず、比較・手順・階層・循環・対立など章の論理に合う構図を選ぶ。
5. **章ごとにプロンプトを起こす**: 後述の【スタイル定型】＋【章のビジュアル設計】＋【その章の正確なテキスト】。表・リスト・ラベルは**本文から逐語コピーして文字列で渡す**（gpt-image の創作・誤字を防ぐ）。

6. **Q&A で1枚試作 → 合意 → 一括生成**: いきなり全章作らない。まず代表的な1枚（比較・階層・フローなど、中央の大きな絵を作りやすい章）を生成して見せ、情報密度・手描き感・文字量・中心メタファーの分かりやすさを合わせてから残りを生成する。
7. **画像生成（Codex 経由・サブスクルート）**: 下記「画像生成」の通り。試作の1枚は最新ファイル（`ls -t ~/.codex/generated_images/*/*.png | head -1`）を拾えばよいが、**合意後の残りは並列で一括生成する**（下記「複数枚の並列一括生成」）。確定した画像を `<docsディレクトリ>/assets/<資料スラッグ>/<NN>-<slug>.png` へコピーしてマッピングする。
8. **レビュー（必須）**: 生成画像を1枚ずつ開き（Claude Code の場合は `Read` ツールで）、**文字化け・誤字・内容違い**に加え、後述の「章扉インフォグラフィックの合格基準」を確認する。崩れていたらその章だけ再生成。金額・システム名・区分など意味が変わる誤字は特に厳しく見る。

9. **Markdown へ差し込み**: 各章見出しの直後に `![<alt>](assets/<資料スラッグ>/<NN>-<slug>.png)` を1行入れる。**本文の文章・表・コードは触らない**。alt は内容の要約（スクリーンリーダ・検索用）。
10. **commit / push はユーザーの指示があってから**（プロジェクト共通ルール）。ローカル相対パスなので issue 版と違い「画像を先に push しないとリンク切れ」の順序制約はない。push するときは画像と md を同じ commit に入れる。

## 画像の置き場所と参照

- 置き場所: Markdown と同じディレクトリ配下の `assets/<資料スラッグ>/`（リポジトリに規約があればそれに従う）。資料スラッグは英語ケバブケースで資料ごとに切る。
- ファイル名: `<章番号2桁>-<英語slug>.png`（例 `03-hub-and-spoke.png`）。章との対応が追える命名にする。
- 参照は**相対パス**: `![alt](assets/<資料スラッグ>/<NN>-<slug>.png)`。GitHub のファイル表示・各種エディタのプレビューで正しく解決される絶対パス（`/Users/...`）や raw URL は使わない（リポジトリを移動・クローンしても壊れないようにするため）。
- 画像を作り直したときはファイル名を変える必要はない（ローカル参照なのでキャッシュ問題は基本ない）。ただし共有ページなど CDN 経由の閲覧で古い画像が残る場合はファイル名を変えると確実。

## スタイル定型（gpt-image-2 プロンプトに必ず入れる）

狙うのは、整然としたカード型の業務図ではなく、**章の主張を大きな絵で理解させる、高密度な手描きの一枚新聞・学習ノート**。プロンプト冒頭に以下を貼る:

```
組み込みの image_gen ツールを直接使って画像を1枚だけ生成してください。APIキーやスクリプト作成は不要です。OpenAI Images APIを直接叩かないでください。
【成果物】これは資料全体の要約ではなく、1つの章を直感的に理解させる「章扉インフォグラフィック」。日本の手描きインフォグラフィック作家が、太い黒マーカー、色鉛筆、蛍光マーカーを使ってクリーム色の模造紙に描いたような一枚新聞・学習ノート形式にする。
【手描きの質感】主線は太く、黒に近い焦げ茶。枠線・矢印・下線には手描き特有のわずかな揺れ、線幅のムラ、塗り残しを残す。背景は温かいクリーム色の紙(#f7f2e7)で、うっすら紙の繊維感を出す。印刷フォント、均一なベクター線、光沢、3D、写真表現にはしない。

【章の主役】章の中心メッセージを、階段、合流する道路、橋、天秤、建物、循環、分かれ道など、内容に合った「大きな視覚メタファー」へ変換し、紙面中央から約半分を使って主役として描く。本文を角丸カードへ分解して並べるだけにしない。中央の絵だけを見ても、比較・変化・流れ・関係性のどれを説明する章か分かるようにする。
【紙面設計】上部に大きなタイトル、中央に主役の大きな絵、左右または下部に比較・メリット・注意・補足・結論を配置する。すべてを同じ大きさ・同じ形にしない。比較は左右対比、手順は番号付きの流れ、注意は警告欄、結論は下部の帯など、情報の役割ごとに見せ方を変える。適度に高密度だが、中心から周辺へ視線が自然に流れる編集レイアウトにする。
【情報の比重】目安として、紙面の約50%を大きな視覚メタファー、約25%を判断に必要な比較・数値・主要ラベル、約15%をメリット・注意点、約10%を結論・次の行動に使う。比率は章に応じて調整してよいが、主役の絵より補助カードが目立ってはいけない。
【タイトル見出し】上部に、太い黒の手書きゴシック風タイトルを大きく置く。章の重要語だけ赤などのアクセント色にし、タイトル下に赤・黄・青・緑いずれかの太いマーカー線を引く。短いサブタイトルがある場合はその下に置く。本文より明確に大きく、タイトル・カテゴリ名・補足説明の文字サイズに強いメリハリをつける。画像内のタイトル・サブタイトル・バッジには「第3章」「03」などの章番号を一切入れない。章の順番が変わっても、内容が同じなら画像を作り直さず再利用できるようにする。
【文字と強調】本文も読みやすい太めの手書き文字として描く。重要語はマーカー下線、二重線、囲み、丸数字で強調する。固有名詞・数字・比較ラベルは逐語どおりに書く。説明文を長い段落にせず、短い見出し＋1〜3行の箇条書きへ整理する。
【イラスト】中央の主役に加え、人物、システム、PC、スマホ、書類、店舗、商品、チェックリストなど、章の内容を象徴する小さな手描きイラストを3種類以上入れる。人物やシステムは少しデフォルメして親しみやすくするが、幼児向けの絵本にはしない。各イラストは飾りではなく、近くの情報の意味を補助する役割を持たせる。
【色】黒い主線を基調に、赤、マスタードイエロー、青、緑、紫を章内の区分・強調へ使う。色面は完全なベタ塗りではなく、マーカーや色鉛筆の薄いムラを残す。多色でも意味のない虹色にはせず、同じ意味には同じ色を使う。
【装飾】タイトル下のマーカー線、短い放射線、付箋風メモ、チェック、警告、電球、短い吹き出しなどを、内容と関係する場所に適量入れる。余白を完全に均等にせず、人が紙面を編集して埋めたようなリズムを作る。本文と無関係な動物、画材、過剰な星、水彩の飛び散りは入れない。

【禁止】企業向けPowerPointテンプレート、Webダッシュボード、アプリUI、角丸カードだけの構成、均一なグリッド、細いサンセリフ書体、リアルな人物、写真、3D、光沢、ネオン、完全に整ったベクター図形にしない。
【サイズ】横1536 x 縦1024。
日本語は誤字なく正確に描いてください。
```

そのうえで、本文だけを渡して構成を丸投げせず、次の順序で章固有の指示を渡す。

```text
【描く内容：<章タイトル>】
【この章の中心メッセージ】<読者に1つだけ残したいこと>
【使用する視覚メタファー】<大きな絵と、何を何に対応させるか>
【紙面設計】
- 上部：<章番号を除いたタイトルとサブタイトル>
- 中央：<主役の大きな絵>
- 左側：<比較・メリットなど>
- 右側：<注意・補足など>
- 下部：<結論・次の行動など>
【画像内に逐語で描く文字】
- <タイトル>
- <ラベル・数値・短い説明>
【文字の厳守】「<正しい文字列>」と正確に書く。別表記にしない。
```

表は「A｜B｜C」の区切りで列を明示する。ただし元の表をそのまま小さく再現せず、中心メッセージの理解に必要な比較軸だけを周辺情報として組み込む。

### 視覚メタファーの選び方

| 章の論理 | 向いている大きな絵 |
|---|---|
| 段階・成熟度・グレード | 階段、山、レベルアップ |
| 複数経路の統合 | 合流する道路、ハブ駅、漏斗 |
| 導入手順・時間の流れ | 一本道、すごろく、駅の路線 |
| Before / After | 左右に分かれた風景、橋を渡る場面 |
| 循環する業務 | 円形ループ、歯車、季節の巡り |
| 土台と発展要素 | 建物、ピラミッド、樹木 |
| 選択肢・判断 | 分かれ道、天秤、比較棚 |
| 情報の蓄積・整理 | 本棚、引き出し、倉庫 |
| リスクと対策 | 傘、防波堤、盾、セーフティネット |

比喩は装飾ではなく、章の論理構造を見える形へ翻訳するもの。本文にない新しい意味を足さず、同じ資料内でも章ごとに最も自然な比喩を選ぶ。

### スタイルのキモ（ハマりどころ）

媒体によらない共通の作法（**逐語で文字を渡す・カタカナ長音＋「一」の崩れ・生成後レビュー**）は共有スキル `image-gen` の「プロンプト共通の作法とハマりどころ」に従う。ここには章扉スタイル固有のキモだけを挙げる:

- **タイトルは必ず「見出し化」の指定を入れる**（太い手書き文字＋重要語の色替え＋マーカー下線）。指定しないと本文と同じ大きさになり締まらない。
- **画像内に章番号を入れない**。Markdown 見出しが `## 3. 基本方針` でも、画像には `基本方針` だけを描く。「第3章」「03」のような番号バッジも禁止。章順の変更だけなら既存画像を維持し、内容が変わった場合だけ再生成する。

- **先に中心メッセージと視覚メタファーを決める**。これを省くと、画像モデルは本文を均等なカードに分割しがち。中央の大きな絵が章の論理を担い、カードや小物はその理解を助ける脇役にする。

- **可愛さは中庸**。「絵本風・ちびキャラ全開」にすると情報が減って軽くなる。「親しみやすいが整理されている」を狙う。
- **情報密度は文字数ではなく役割の多さで作る**。大きな絵、比較、補足、注意、結論を異なる形で共存させる。小さい文字を大量に詰めることを高密度と取り違えない。
- **装飾は意味のある場所だけに置く**。電球・チェック・警告・短い放射線は使ってよいが、星・鉛筆・水彩・無関係な動物を一律に散らさない。
- **1枚に詰めすぎない一方、情報は削らない**。章の内容が多い場合は「その章の地図」になる粒度（中心メッセージ＋主要ラベル＋判断材料）に要約してよいが、固有名詞・数字は逐語で。

### 章扉インフォグラフィックの合格基準（必須）

このスキルの成果物は「読みやすい図表」ではなく、**手書き風イラスト入りインフォグラフィック**。文字精度を理由に HTML/CSS/Playwright/SVG で図表画像を組むのは禁止。文字化けが不安な場合は、HTML図表へ逃げず、画像内テキストを短く・正確な語句に絞って gpt-image-2 に描かせる。

各インフォグラフィックには、**その資料のドメインに合った小物・キャラ**を少なくとも3種類以上、目に見えるイラストとして入れる。例:

- 人物（スタッフ / 管理者 / お客様 / 担当者など）
- フレンドリーな Bot・システム・サーバー
- 店舗・商品（楽器店案件ならギター・アンプ・レジ、会計案件なら請求書・お金、など案件固有のモノ）
- 書類・契約書・台帳・スプレッドシート
- スマホ・PC・通知画面
- フォーム・メール・チェックリストなど、その章固有の道具

次のような成果物は、たとえ文字が正確でも不合格:

- 章の中心メッセージを表す大きな絵がなく、小カードが均等に並んでいる
- 角丸カードと矢印だけの業務フロー図
- HTML/CSS で整えた説明スライド風の画像
- 人物・システム・商品・書類などの小物がほぼない図表
- 「読みやすいが、手書き風イラスト入りではない」画像
- マスコット1体＋ラベル数個だけのスカスカなポスター（キャラが大きく余白が広く、文字情報が薄い画像）
- 背景だけ紙風で、文字・枠線・矢印が均一なデジタル図形に見える
- 文字を詰め込みすぎて、タイトル→中央の絵→周辺情報という視線の順序がない

1枚試作では、次を順に確認する。1つでも外れたら残りを生成せず、その1枚を作り直す。

1. **3秒理解**: 縮小表示でもタイトルと中央の大きな絵から、章の主張が推測できる。
2. **主従**: 中央の視覚メタファーが主役で、補助カードや小物より強い。
3. **情報密度**: 比較・補足・注意・結論など複数の役割がありながら、視線が迷わない。
4. **手描き感**: 太い黒線、線の揺れ、マーカーのムラ、クリーム紙の質感がある。
5. **ドメイン性**: その章固有の人物・システム・商品・書類などが3種類以上ある。
6. **文字精度**: 固有名詞・数字・区分・日付に誤字や創作がない。
7. **章順から独立**: タイトル、サブタイトル、バッジ、隅の注記に章番号が描かれていない。

最終レビューでは、全画像を順に `Read` で開き、まとめて「同一トーンの手書き風イラスト群」に見えるか確認する。図表・カードUIに見えるものは差し替える。

## 画像生成（Codex 経由・API 課金を発生させない）

**呼び出し規約の正本は共有スキル `image-gen`**（同じ共有層から配布。前提としてこのスキルと併せて導入する）。**生成前に必ずそれを読み、「画像生成（Codex 経由・API 課金を発生させない）」「複数枚の並列一括生成」の前提確認・呼び出し方・ハング打ち切り基準・保存の注意にそのまま従う**（`< /dev/null` 必須、`--cd` はスクラッチディレクトリ、保存・リネームはスクリプト側、gpt-image-2 の制約、`parallel-imggen.sh` の使い方など、エンジンの手順・数値をここに複製しない）。

本リポジトリ向けに読み替えるのは次だけ:

- スクリプトの場所: image-gen スキルの `scripts/parallel-imggen.sh`
- 確定した画像のコピー先: `images/` ではなく `<docsディレクトリ>/assets/<資料スラッグ>/<NN>-<slug>.png`（最終確認はスクラッチの候補ファイルではなく assets 配下の最終ファイルを開いて行う。Claude Code の場合は `Read` ツールで開く）
- upstream の「置き場所と公開 URL」「push = 社外公開」の節は技術ブログ（apps/tech）固有なので無視する（本リポジトリの配置・共有は本スキルと docs-share の規約が正）

並列化しても「1枚試作 → 合意 → 残りを一括」の順序と、生成後のレビュー（1枚ずつ開いて誤字確認。Claude Code の場合は `Read` ツールで開く）は省略しない。

## Markdown への差し込み例

章見出しの直後に画像1行を足すだけ（本文はそのまま）:

```markdown
## 3. こちらの基本方針（アーキテクチャの考え方）

![ハブ&スポーク構成：商品マスタを1つに固定し、全チャネルはマスタとだけ会話する。更新は1回→全チャネルへ配信](assets/tc-gakki-brief/03-hub-and-spoke.png)

### コア概念: ハブ&スポーク（マスタ一元化）
…（既存本文はそのまま）
```

## やらないこと / 注意

- 本文の文章・表・コードブロック・リンクを書き換えない（差し込むのは画像行だけ）。
- Markdown を HTML に変換しない（それは md-to-visual-html の仕事）。
- HTML/CSS/Playwright/SVG で「画像化した図表」を作って代替しない。最終成果物は、ユーザーが明示しない限り gpt-image-2 で生成した手書き風イラスト入り画像にする。
- イラストのみで文字を入れない作り方をしない（読めない絵になる。issue 版で全差し替えになった failure mode）。
- 大量の章を**確認なしに一括生成しない**。1枚合意してからバッチ。
- 確定した内容（金額・システム名・区分・日付）が画像で誤字になっていないか必ず目視。意味が変わる誤字は再生成。

- commit / push はユーザーの明示指示があるまでしない（グローバルルール・リポジトリ運用方針）。
