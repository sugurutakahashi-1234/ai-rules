# flyer-designer

A4チラシを「Webページ化」ではなく「配布・印刷される1枚の広告物」として作る。目的は、情報を全部載せることではなく、対象者が自分ごと化して申し込み・問い合わせ・来場に進む1枚を作ること。

## Workflow

1. 入力資料を読み、次を内部で決める。
   - 誰に配るチラシか
   - 何を申し込ませる・問い合わせさせる・覚えてもらうチラシか
   - 読者が最初に反応する言葉は何か
   - 信頼材料、開催情報、申込導線のうち何が確定・未確定か
2. 既存ファイル更新か新規作成かを確認する。既存チラシを上書きすると衝突しそうな場合は、別名で新規作成する。
   - 既存の標準名PDF（例: `イベント名_チラシ.pdf`）がある場合、読者やユーザーはそちらを開きやすい。別名でv2を作っただけで終わらず、標準名を更新するか、どちらを開くべきかを明示する。
3. 必要な素材を集める。
   - ロゴ、登壇者写真、QR、会場写真、商品写真など、実在感を出す素材を優先する
   - 会社・ブランド固有の素材が必要な場合は、会社共有層のスキルやリポジトリ側の素材ガイドを参照する
   - 素材がない場合は、生成画像より先に「写真枠」「QR準備中」「日時調整中」など差し替えやすい枠を作る
4. A4片面の情報設計を作る。
   - ファーストビュー: タイトル、対象者、自分ごと化する問い or ベネフィット
   - 信頼: 主催、登壇者、会社、実績、対象者に近い事例
   - 内容: 当日わかること・見られることを3〜5点に絞る
   - 詳細: 日時、場所、対象、参加費、定員など
   - 行動: 申込QR、問い合わせ、公式サイトQR
5. デザイン方向を対象者ごとに決める。既定のクリーム/手書き風へ固定しない。
   - 地元中小企業・法人会・商工会: 信頼感、読みやすさ、明るさ、実在感。写真と余白を使い、過度にITっぽくしない
   - SaaS/IT系: シャープ、情報密度高め、機能価値を明確に
   - 採用/若年層向け: 人物写真、勢い、参加後の変化
   - 行政/公共寄り: 落ち着き、明確な開催情報、安心感
6. HTMLでA4原稿を作る。
   - `@page { size: A4 portrait; margin: 0; }`
   - 画面確認用にも印刷用にも使えるよう `210mm x 297mm` の `.sheet` を作る
   - 外部CDN、外部フォント、外部スクリプトは使わない
   - 画像は相対パスで参照し、base64 data URIにしない
   - 未確定情報は差し替えやすいテキスト枠にする
7. Playwright等でPDF/PNGを書き出す。
   - A4 PDF: 印刷・共有用
   - PNG: チャット確認・SNS/Slack共有用
   - HTML: 後から文言や日時を直す編集元
8. 必ず視覚確認する。HTMLスクリーンショットだけで終わらない。
   - A4内に全要素が収まっているか
   - 要素同士が重なっていないか。`overflow` が0でも、固定配置の下部情報が本文にかぶることがある
   - 文字が小さすぎないか
   - 余白不足、文字被り、QR潰れ、写真の不自然なトリミングがないか
   - 目線がタイトル→価値→詳細→申込へ流れるか
   - 最終PDFを `pdftoppm` 等でPNG化し、PDFそのものが意図したデザインになっているか確認する

## Design Rules

- A4チラシは情報を詰め込みすぎない。本文説明より、見出し・短い箇条書き・視覚要素で理解させる。
- 「A4なので全部載せる」ではなく、申し込みに必要な情報だけを残す。
- 2時間の詳細プログラム表は、A4片面では情報過多になりやすい。集客チラシでは「当日お見せすること」3〜5点に圧縮し、詳細タイムラインは別紙・Web・当日配布に逃がしてよい。
- タイトルは資料名ではなく、読者が反応する問い・約束・変化にする。
- 色は案件ごとに選ぶ。茶色/黄色/クリーム系は、温かい手書き資料に合う場合だけ使う。
- 登壇者がいるチラシでは、写真と肩書きを入れて実在感を出す。写真なしの抽象図だけにしない。
- QRは印刷後に読める大きさを確保する。小さくても20mm角程度を目安にする。
- 日時・会場・申込先が未確定なら、無理に確定情報のように書かず「調整中」「準備中」として目立ちすぎない枠にする。
- AIセミナーのチラシでは、抽象的な「DX」「AI活用」だけでなく、読者の仕事に近い具体例を見出しに置く。

## Output Naming

入力Markdownと同じフォルダに作る場合:

- 編集元HTML: `<YYYYMMDD>_<イベント名>_チラシ_A4.html`
- 確認用PNG: `<YYYYMMDD>_<イベント名>_チラシ_A4.png`
- 印刷用PDF: `<YYYYMMDD>_<イベント名>_チラシ_A4.pdf`
- 素材: `assets/<slug>/`

既存ファイルがある場合は、上書きせず `_v2` やテーマ名を付けた別名で作る。

ただし、既に配布・確認で使われている標準名PDFがある場合は、最後に次のどちらかを必ず行う。

- 標準名PDFも新デザインに差し替える
- 標準名PDFは旧版のまま残し、ユーザーに「新デザインはこの別名PDF」と明示する

ユーザーが「PDFが古い」「色が違う」と言った場合は、まず開いているファイル名を疑う。新旧PDFを `pdftoppm` で画像化し、標準名PDFと別名PDFのハッシュを比較する。

## Validation

レンダリングには、ローカルの Playwright（無ければ実行環境に同梱の Node ランタイム）で render スクリプトを実行する。

```bash
node render-flyer.js  # Playwright が使える Node 環境で
```

最後に `view_image` でPNGを開き、A4内に収まっているか目視確認する。可能ならPDFも生成し、ファイルサイズとページ数を確認する。

PDF確認の最低ライン:

```bash
pdftoppm -png -singlefile -r 150 <flyer.pdf> /tmp/flyer-rendered
pdfinfo <flyer.pdf> | sed -n '1,18p'
```

`/tmp/flyer-rendered.png` を `view_image` で開き、HTML/PNGではなくPDF本体が正しい色・レイアウトになっていることを確認する。

重なり確認の考え方:

- A4外にはみ出していないだけでは不十分
- `position: absolute` の下部情報、QR、注記、写真ラベルは本文カードにかぶりやすい
- 最終PNGで、開催概要・QR・講師ラベル・フッターが他要素を隠していないかを見る
- 検出が必要なら、主要ブロック（hero/content/bottom/footer）の `getBoundingClientRect()` を出力し、上下関係を確認する
